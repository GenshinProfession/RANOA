# RANOA 云同步中心技术方案

## 1. 目标与结论

云同步中心的目标不是把 `~/.pi/agent` 当作共享网盘直接覆盖，而是建立一个有版本、可合并、可回滚、端到端加密的同步系统。

核心结论：

1. 服务器是版本顺序和设备权限的权威，不是内容取舍的权威。
2. 已授权设备默认地位相同，不以“最后上传者”“系统时间较新者”或“某台主设备”决定胜负。
3. 每次修改必须携带它基于的服务端版本；服务端只接受基于当前版本的更新，否则返回冲突。
4. 可安全合并的数据自动合并；无法证明可安全合并的数据保留双方，绝不静默覆盖。
5. 活跃会话通过写入租约避免两台设备同时发送；离线并发发生后转成会话分支或冲突副本。
6. 云端只保存密文、版本元数据和不可逆对象标识；SSH 密钥永不进入同步范围。

## 2. 已有环境与数据盘点

### 本地

- RANOA/Pi 使用 `PI_CODING_AGENT_DIR` 指向独立 Agent 数据目录。
- 当前 Agent 数据约 108 MB，其中会话约 65 MB、npm 运行资源约 33 MB、技能约 1.9 MB。
- 关键数据包括 `sessions/`、`settings.json`、`models.json`、`auth.json`、`skills/`、`extensions/` 与插件声明。
- 浏览器侧存在语言、壁纸、声音、工具预设、侧边栏宽度、文件面板状态、未读状态和最近工作区等偏好。
- 会话文件包含本机绝对路径，跨 Windows/Linux 时必须经过工作区映射，不能原样覆盖。
- 当前草稿存放在进程内存，刷新或进程退出会消失，需要先持久化后才能参与同步。

### 服务器

- Ubuntu 24.04 LTS，8 核，约 15 GB 内存，根盘约 227 GB 可用。
- Docker、Node.js、Nginx、systemd 已具备。
- 资源足以运行同步 API、PostgreSQL 和本地对象存储；暂时不必引入 MinIO 集群。

## 3. 同步数据分类

| 数据类别 | 默认策略 | 冲突处理 | 备注 |
|---|---|---|---|
| 会话 JSONL | 双向同步 | 语义合并、分支或冲突副本 | 不按整文件最后写入覆盖 |
| 会话附件/图片 | 不可变对象 | 按内容哈希去重 | 分块、断点续传 |
| 模型配置 | 双向同步 | 按 provider/modelId 合并，同字段冲突确认 | 密钥字段单独处理 |
| 通用设置 | 双向同步 | 按字段版本合并 | 数组/复杂对象作为原子值 |
| 技能与手写扩展 | 双向同步 | 文本三方合并，失败则冲突副本 | 保留用户手改内容 |
| 插件安装状态 | 同步声明并重装 | 按包名和版本合并 | 不同步平台相关 node_modules |
| Provider 凭据 | 默认设备私有；可选共享保险库 | 同一 provider 不自动覆盖 | 全程端到端加密 |
| `trust.json` | 仅本机 | 不同步 | 不能让一台设备替另一台信任项目代码 |
| `bin/`、`npm/`、缓存 | 不同步 | 从声明重建 | 避免平台差异和无效流量 |
| 工作区本地路径 | 每设备独立映射 | 不冲突 | `workspaceId -> localPath` |
| 语言/壁纸/声音/工具预设 | 可漫游 | 按字段版本 | 用户可关闭 |
| 面板宽度、展开状态、未读状态 | 仅本机 | 不同步 | 属于设备布局状态 |
| 草稿 | 可漫游 | 每会话保留多设备版本 | 需先落盘持久化 |

## 4. 总体架构

```text
Browser UI
  └─ Settings / Cloud Sync
       └─ Local RANOA API (/api/sync/*)
            └─ Local Sync Agent
                 ├─ Pi data adapters
                 ├─ browser preference adapter
                 ├─ local SQLite journal / offline queue
                 ├─ chunker + encryptor
                 └─ HTTPS
                      └─ Nginx
                           └─ RANOA Sync API
                                ├─ PostgreSQL: devices, revisions, cursors, leases
                                └─ CAS directory: encrypted chunks
```

本地同步逻辑运行在 RANOA 的服务端进程或独立 `ranoa-syncd` 中，浏览器不直接持有云端管理凭据。首期可在 Next.js 服务内使用全局单例，稳定版拆成独立守护进程，避免热更新或浏览器关闭中断同步。

服务端建议放在仓库的 `services/sync-server/`，采用 TypeScript + Fastify + PostgreSQL。加密对象先存服务器本地 CAS 目录，接口抽象为 ObjectStore，未来可无缝换成 MinIO/S3。

## 5. 多设备信任与一致性模型

### 5.1 设备身份

- 每台设备首次连接时生成独立 `deviceId` 和设备密钥对。
- 新设备必须使用一次性配对码，由已有 Owner 设备或服务器 CLI 批准。
- 设备角色：`owner`、`full`、`read_only`、`revoked`。
- 不允许两台机器复制并共用同一个 deviceId；检测到克隆身份时暂停同步并要求重新注册。
- 管理用 SSH 私钥不属于设备同步凭据，也不允许上传。

### 5.2 不信任客户端时间

每次更新包含：

```ts
interface SyncMutation {
  operationId: string;      // 幂等重试
  deviceId: string;
  objectId: string;
  baseRevision: number;     // 客户端编辑时看到的版本
  schemaVersion: number;
  encryptedManifest: string;
}
```

服务端为每次成功提交分配递增 `serverSequence`。设备时间只用于界面展示，不参与冲突判断，因此时区错误、时钟回拨和夏令时不会破坏同步。

### 5.3 谁的数据可信

没有固定“主设备”。判断顺序如下：

1. 权限是否合法、设备是否被撤销。
2. 更新是否基于当前 revision。
3. 对象类型是否允许无损合并。
4. 无法无损合并时同时保留两份，等待用户选择或生成分支。

管理员可以在数据分类上设置策略，但危险策略（始终以本机覆盖云端、始终以云端覆盖本机）只允许作为一次性恢复动作，不能作为后台默认策略。

## 6. 冲突处理矩阵

| 场景 | 处理方式 |
|---|---|
| 两台设备分别新建不同会话 | 直接并集，两边都会看到 |
| 两台设备从同一份数据复制而来 | 会话 UUID + 内容哈希去重，不产生重复会话 |
| 同一会话在两台在线设备同时发送 | 发送前获取写入租约；第二台进入只读并提示接管 |
| 同一会话在两台离线设备都追加 | 有共同基线且仅追加时按 entryId 合并成会话树；否则把后上传版本变成冲突分支/独立 fork |
| 一台删除、另一台离线修改 | 删除产生 tombstone；修改内容放入“已恢复的冲突副本”，不复活原对象 |
| 设置文件修改不同字段 | 自动字段级合并 |
| 同一设置字段同时修改 | 保留双方值，在冲突中心选择；当前设备继续使用本地值 |
| 技能文本同时修改 | 基于共同祖先做三方合并；失败时生成 `.conflict-<device>` 副本 |
| 二进制附件冲突 | 作为两个不可变对象保留 |
| 两台设备登录同一 provider 的不同 Token | 默认分别保存在设备凭据中；只有显式“发布到共享保险库”才跨设备使用 |
| 新设备没有对应项目目录 | 会话可浏览，但发送按钮禁用，直到完成工作区路径映射 |
| Windows 与 Linux 路径不同 | 使用逻辑 workspaceId 映射，不比较绝对路径 |
| 老版本客户端遇到新 schema | 只读兼容；低于 `minReaderVersion` 时拒绝写入并提示升级 |
| 上传中断或重复请求 | 分块续传，operationId 幂等，不产生重复 revision |
| 文件损坏 | 每块和总 manifest 校验；损坏版本隔离并回退到上一 revision |
| 服务器从旧备份恢复 | server epoch 改变，客户端停止自动推送并要求恢复确认，避免旧云端覆盖新本地 |

## 7. 会话同步专项设计

会话不能当普通文本文件同步，因为 Pi 会追加内容，也可能在分支、迁移、删除时重写整个文件。

### 正常路径

1. Agent 运行期间不上传未完成文件。
2. 收到 `prompt_done`/`agent_settled` 且文件静默一小段时间后生成快照。
3. 解析 session header 与每条 entry 的 id、parentId、类型和内容哈希。
4. 上传增量 manifest 与新增块。
5. 其他设备拉取后，通过 workspace 映射物化成本机可用的 JSONL，并重写本机相关 `cwd`、`parentSession` 路径。

### 写入租约

- 租约只在真正发送消息时获取，浏览会话不占锁。
- 租约有短 TTL，并由运行中的 Agent 续约。
- 正常完成后主动释放；设备断网后由 TTL 自动失效。
- 用户可以“接管”，但必须先生成快照；接管行为进入审计记录。

### 离线分叉

离线设备允许继续工作。重连时若发现共同基线后的 entryId 完全不同且父链合法，可合并为 Pi 的会话树；如果旧条目被重写、删除或出现同 id 不同内容，则保留原云端会话并创建 conflict fork。任何路径都不丢消息。

## 8. 工作区与跨设备路径

每个项目在云端使用随机 `workspaceId`。本机维护：

```ts
interface DeviceWorkspaceMapping {
  workspaceId: string;
  localPath: string;
  gitRemoteFingerprint?: string;
  lastVerifiedAt: string;
}
```

Git remote 只能用于辅助匹配，不能直接作为唯一身份；没有 Git 的目录也可同步会话。路径映射只保存在对应设备。若项目尚未克隆，新设备可以浏览会话历史，但工具调用和继续对话保持锁定。

项目源码本身不进入云同步中心，仍由 Git 管理。项目级 `.pi/`、`.agents/skills` 是否跟随项目同步，默认由 Git 处理；只有用户明确选择后才加入云同步范围。

## 9. 端到端加密与凭据

### 密钥层级

- 用户创建同步保险库时生成随机 Vault Key。
- 每台设备持有自己的公私钥；Vault Key 分别封装给已授权设备。
- 数据块使用派生的数据密钥和 AES-256-GCM 加密。
- 对象 ID 使用 HMAC 生成，使服务器无法根据普通 SHA-256 反查内容，同时可在同一保险库内增量去重。
- 服务器数据库、对象目录和日志均不得记录明文 Token、会话内容、项目路径或密钥。

### 恢复

- 创建保险库时提供一次恢复码，用户必须离线保存。
- 丢失全部设备私钥且没有恢复码时，服务器无法解密，这是端到端加密的必然结果。
- 撤销设备会阻止其继续拉取/上传，但无法远程删除该设备此前已下载的本地副本。

### Provider 凭据策略

凭据默认设备私有。用户可把某个 provider 凭据显式发布到“共享凭据保险库”，并为其命名、设置允许设备和过期时间。新设备恢复后必须执行 provider 健康检查；失效的 OAuth/Token 显示为“需要重新认证”，不能阻塞其他数据恢复。

## 10. 增量、离线与删除

- 文件按约 4 MiB 分块，manifest 记录块顺序、大小、密文哈希和 schema。
- 本地 SQLite 保存 objectId、已知 revision、扫描哈希、离线操作和服务端 cursor。
- 文件监听只用于加速发现，定期全量扫描用于修复漏事件。
- 失败采用指数退避，恢复后从缺失块继续。
- 删除使用 tombstone，默认保留 30 天；离线旧设备不能让已删除对象静默复活。
- 每次危险合并、批量删除、首次拉取前自动生成快照。

## 11. 服务端核心数据模型

主要表：

- `vaults`：保险库、schema、server epoch。
- `devices`：设备公钥、角色、状态、最后在线时间。
- `workspaces`：逻辑项目身份和加密元数据。
- `objects`：对象类型、当前 revision、删除状态。
- `object_revisions`：base revision、提交设备、server sequence、加密 manifest。
- `chunks`：密文块地址、大小、引用计数。
- `revision_chunks`：revision 到块的有序映射。
- `sync_cursors`：每设备已经确认的 server sequence。
- `session_leases`：会话写入设备、过期时间、runId。
- `snapshots`：恢复点及保留策略。
- `audit_events`：配对、撤销、接管、回滚和危险操作。

服务端所有更新在数据库事务中提交；对象 manifest 成功持久化后才推进 revision 和 cursor。

## 12. 接口设计

### 配对与设备

- `POST /v1/pairing/codes`：Owner 生成一次性配对码。
- `POST /v1/pairing/complete`：新设备提交公钥并换取设备凭据。
- `GET /v1/devices`：设备列表、角色、最后同步状态。
- `PATCH /v1/devices/:id`：改名、角色调整、撤销。

### 同步

- `POST /v1/sync/plan`：提交本地索引，返回上传、下载、冲突和删除预览。
- `GET /v1/changes?after=<cursor>`：增量读取服务端变更。
- `HEAD/PUT /v1/chunks/:chunkId`：检查与上传密文块。
- `GET /v1/chunks/:chunkId`：下载密文块。
- `POST /v1/objects/:id/commit`：带 baseRevision 的乐观并发提交。
- `POST /v1/conflicts/:id/resolve`：记录用户选择并生成新 revision。

### 会话租约与恢复

- `POST /v1/sessions/:id/lease`：获取或续约写入租约。
- `DELETE /v1/sessions/:id/lease`：释放租约。
- `GET/POST /v1/snapshots`：查看和创建恢复点。
- `POST /v1/snapshots/:id/restore-plan`：只生成回滚预览。
- `POST /v1/snapshots/:id/restore`：确认后回滚。

### 本地 RANOA API

- `/api/sync/status`、`/connect`、`/scan`、`/plan`、`/run`。
- `/api/sync/conflicts`、`/devices`、`/scope`、`/workspace-mappings`。
- 浏览器只调用本地 API，所有文件读取、加密和云端认证均在本地服务端完成。

## 13. 设置界面规划

在现有设置树新增“云同步”，内部采用左右结构：

1. **概览**：连接状态、最后同步、待上传/待下载、冲突数、当前阶段和进度。
2. **同步范围**：会话、设置、模型、技能、插件声明、界面偏好、共享凭据开关。
3. **设备**：设备名称、角色、指纹、最后在线、撤销与重新配对。
4. **工作区映射**：云端项目与当前机器目录的对应关系。
5. **冲突中心**：左右差异、保留两份、合并、使用本地、使用云端。
6. **版本与恢复**：快照、回收站、单对象回滚和全量恢复预览。

首次连接必须先展示同步计划，默认按钮为“安全合并双方”。“用本机覆盖云端”和“用云端替换本机”放入高级危险操作，并要求二次确认与自动快照。

同步状态机：`未连接 → 配对中 → 扫描中 → 计划待确认 → 同步中 → 已同步`，异常状态包括 `离线排队`、`存在冲突`、`密钥不可用`、`服务器回滚待确认`。每个状态都应有明确动画和可读文字，不能只依赖旋转图标。

## 14. 分阶段开发与验收标准

### 阶段一：安全连接与手动备份/恢复

开发内容：

- 建立 `sync-server`、PostgreSQL、加密对象目录和 Nginx HTTPS。
- 完成设备配对、端到端密钥、数据扫描器、manifest、分块上传和本地同步状态库。
- 设置中心加入云同步概览、同步范围和首次同步预览。
- 先覆盖 sessions、settings、models、skills、extensions；凭据默认不上传。

验收标准：

- 当前约 108 MB 数据可在网络中断后续传完成。
- 服务端磁盘和数据库中搜索不到会话明文、Token 和本地路径。
- 恢复到独立测试目录后，纳入范围的数据哈希一致，原始 Pi 和 RANOA 数据均不被覆盖。
- 同一个操作重复提交不会生成重复对象或重复 revision。
- 首次连接在“本地与云端都有数据”时只展示计划，未确认前不写任何一侧。

### 阶段二：自动同步与双设备并发

开发内容：

- 文件监听 + 周期扫描、离线队列、增量 cursor、tombstone。
- 会话写入租约、并发检测、冲突中心、设置字段级合并。
- 设备管理、撤销、只读角色和审计日志。

验收标准：

- A/B 两台设备分别新建会话后，双方最终都能看到，且不重复。
- A/B 同时修改同一会话时，不丢任何消息；在线时第二台被租约阻止，离线时生成合法分支或冲突副本。
- 删除与离线修改并发时，原对象保持删除，修改内容进入恢复区。
- 人为调整设备系统时间前后 24 小时，不影响冲突判断。
- 断网、服务重启、客户端重启后均能继续同步且不重复提交。

### 阶段三：完整迁移与跨平台恢复

开发内容：

- 工作区逻辑身份、Windows/Linux 路径映射、插件声明重建。
- 浏览器漫游偏好和草稿持久化。
- 可选共享凭据保险库、provider 恢复后健康检查。

验收标准：

- 新 Windows/Linux 设备只需安装 RANOA、配对、映射项目，即可浏览历史并继续会话。
- `bin/`、`npm/` 不从旧平台复制，但插件和依赖可按声明自动恢复。
- 未映射项目只能浏览，不能误在错误目录执行工具。
- 共享凭据关闭时任何 Token 都不跨设备；开启时服务器仍无法读取明文。

### 阶段四：生产化运维

开发内容：

- 自动快照、回收站、单对象/全量回滚、配额、监控和告警。
- server epoch、数据库迁移、客户端兼容窗口、外部备份导出。
- 速率限制、失败锁定、审计导出和灾难恢复演练。

验收标准：

- 可从任意保留快照生成恢复预览并成功回滚。
- 撤销设备后其所有新请求立即失败，其他设备不受影响。
- 从服务器备份恢复后客户端检测到 epoch 变化，不会自动把旧云端覆盖到新本地。
- 数据库损坏、对象块缺失、磁盘不足均有明确错误和只读保护。

## 15. 明确禁止的实现方式

- 不直接把 `.pi/agent` 放到 NFS/WebDAV/SMB 供多机同时写。
- 不使用 rsync 的 `--delete` 或“最后修改时间较新者获胜”作为同步核心。
- 不把一台设备永久设成数据主机；设备下线后不应阻塞其他设备。
- 不同步 SSH 私钥、项目信任状态、平台相关二进制目录和缓存。
- 不在正在生成回复时复制半写入的 session 文件。
- 不在没有预览和快照时执行全量覆盖、批量删除或回滚。

## 16. 推荐实施顺序

先完成阶段一的端到端闭环，但服务端数据模型从第一天就保留 device、revision、cursor、tombstone 和 lease 字段，避免以后推翻协议。阶段一通过独立测试目录完成恢复验证后，再开启自动同步；凭据共享和跨平台自动重建放到阶段三，不能为了“看起来全量”而提前牺牲安全性。
